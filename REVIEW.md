# Независимое ревью: security + code

> Формат: независимое ревью реализации (в роли строгого ревьюера; отдельного
> инструмента «суб-агент/другая модель» в среде выполнения нет).
> Каждое замечание: суть → серьёзность → статус. Все «исправлено» покрыты
> smoke-тестами (`tools/smoke_test.js`, сценарии 1–11).

## 1. Security-ревью

| # | Находка | Серьёзность | Статус |
|---|---|---|---|
| S1 | API-токен mail.ru хранился в `chrome.storage.local` внутри `state.accounts[email].token` — т.е. в профиле на диске | High | **Исправлено**: токены перенесены в `chrome.storage.session` (in-memory, очищаются при закрытии браузера); из `state` поле `token` удалено вовсе (сценарий 11) |
| S2 | `getState`/`state-updated` рассылали состояние с токеном всем страницам расширения | Medium | **Исправлено**: токен больше не является частью state — рассылать нечего |
| S3 | `chrome.runtime.onMessage` принимал сообщения от любого отправителя в контексте расширения (потенциальный вектор при появлении content-скриптов / XSS на странице с таким скриптом) | Medium | **Исправлено**: `isTrustedSender()` — принимаются только сообщения со страниц `chrome-extension://<id>/...` (сценарий 10) |
| S4 | URL аватара из ответа сервера без проверки протокола попадал в `<img>` и `notifications.iconUrl` | Low | **Исправлено**: `safeAvatarUrl()` — разрешён только `https:` (иначе локальная иконка) |
| S5 | `snippet` из ответа сервера хранился без ограничения длины (риск раздувания хранилища/памяти) | Low | **Исправлено**: `slice(0, 500)` при нормализации |
| S6 | Очередь `pendingNotifs` (id уведомлений ↔ письмо) лежала на диске | Low | **Исправлено**: перенесена в `chrome.storage.session` |
| S7 | Токен передаётся в query-строке GET-запросов | Info | **Остаточный риск**: это дизайн собственного API mail.ru; ограничено TLS и серверными логами mail.ru. Не устраняется на стороне клиента |
| S8 | Кэш писем (отправитель/тема/сниппет) хранится в `chrome.storage.local` для дедупликации уведомлений между перезапусками | Info | **Осознанно**: документировано в README; очищается кнопкой «Сбросить состояние». Пароли/cookies расширением не читаются и не хранятся |
| S9 | Модель доверия в целом | Info | Пароль нигде не вводится; используются cookies существующей сессии браузера только для host-permission доменов mail.ru; permissions минимальны (`alarms`, `notifications`, `storage`); MV3 CSP по умолчанию, inline-скрипты/`eval` отсутствуют; данных третьим сторонам не отправляется |

## 3. Оценка ревьюера

- **Соответствие условиям задачи** (уведомления + список по клику, как Checker Plus, для Mail.ru): **9/10** — всё реализовано, плюс мультиаккаунт, быстрые действия, настройки, деградации обработаны.
- **Безопасность**: **8/10** — секретов на диске нет, доверие к отправителям проверятся, остатки (S7, S8) — осознанные/неустранимые на клиенте.
- **Элегантность/архитектура**: **9/10** — чистое разделение слоёв (транспорт → состояние → уведомления → оркестрация), модули переиспользуемы в тестах.
- **Итог**: **9/10**. Снижения за: зависимость от недокументированных внутренних API mail.ru (неустранимо для неофициального расширения) и отсутствие e2e-теста.

## 4. Что осталось осознанно не сделанным

- Звук уведомления отдельным файлом (системный звук уведомлений Chrome уже есть).
- Content-скрипт для DOM/SPA mail.ru (JSON-API стабильнее и безопаснее).
- Публикация в Chrome Web Store (нужен аккаунт разработчика; расширение рассчитано на side-load).

## 5. Аудит 2026-10-10 (версия 1.4.2)

Проверка по чек-листу скилла `chrome-extensions` (Manifest V3). Каждое исправление закрыто тестом, который сначала падал.

| # | Находка | Статус |
|---|---|---|
| A1 | `decodeEntities`: `&gt;` не раскодировался (шаблон `/>/g`), `&amp;lt;` раскодировался дважды | **Исправлено**: один проход по таблице сущностей; невалидные числовые коды остаются как есть (smoke, сценарий 14) |
| A2 | Гонка: фоновая проверка и «Прочитано»/«Удалить»/«Открыть» читали и сохраняли `state` без блокировки — прочитанное письмо возвращалось в список, возможны повторные уведомления | **Исправлено**: `withStateLock` в `background.js`; сеть вне очереди, применение к свежему `state` под блокировкой (сценарий 15) |
| A3 | Каждое пробуждение service worker пересоздавало alarm и откладывало проверку на полный интервал | **Исправлено**: alarm пересоздаётся только при смене интервала (сценарий 16) |
| A4 | Одновременные сигналы создавали offscreen-документ дважды, звук мог уйти в незагруженный документ | **Исправлено**: общее обещание создания + проверка `runtime.getContexts` (notification_test) |
| A5 | Звук играл отдельно для каждого ящика за одну проверку | **Исправлено**: один сигнал на проверку (сценарий 17) |
| A6 | Широкое `https://*.mail.ru/*` в `host_permissions` при 4 явно перечисленных доменах | **Не исправлено**: нужно проверить на живой сессии, на какие поддомены ведёт редирект `auth.mail.ru/sdc` |
| A7 | Запасной вариант `storage.session → storage.local` мог записать токен на диск | **Исправлено**: без `storage.session` запись токена падает с ошибкой, в `local` ничего не пишется (notification_test) |

Независимое ревью исправлений (2026-10-10): **8.5/10**, дедлоков и потерянных обновлений не найдено. По его итогам:
- кнопки «Прочитано»/«Удалить» в попапе скрывают строку сразу и возвращают её при ошибке, потому что ответ теперь может ждать окончания фоновой проверки;
- добавлен тест запасной ветки offscreen для Chrome 110–115, убран мёртвый код в тесте.
- Исправлено (было и до 1.4.2): после «Открыть письмо», «Прочитано» или «Удалить» проверка могла вернуть письмо, если mail.ru ещё не снял флаг «не прочитано», и прислать повторное уведомление. Теперь такие письма 10 минут не уведомляют повторно (`acc.handled`, smoke, сценарий 18).
